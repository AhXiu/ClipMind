# 第二阶段：关联发现与主题归纳

## 使用方式

1. 在卡片详情点击“查找本地关联”：对最近 300 张未删除卡片做本机词语重合检索，最多推荐 5 张。不发送网络请求，不要求启用 AI。这里只判断可能同主题，不宣称是向量语义检索。
2. 查看候选中的词语依据、两侧原文和关系方向，确认或忽略。忽略后同一卡片对不再自动推荐；确认后的关系沿用已有 Obsidian ZIP 双链导出。
3. 在卡片库长按选择 2–8 张卡片，点击“多卡归纳”；也可在关联候选上点击“归纳这两张卡片”。确认框逐张展示将发送的完整正文、内容版本和调用路径。
4. 确认后生成主题标题、要点、共同观点、分歧或待验证问题，以及可选关系候选。没有可靠关联时允许返回空关系，不强迫模型制造冲突。
5. 在 AI 工作台查看最近 50 份主题笔记。引用可跳转到当前卡片；支持复制带引用和来源版本的 Markdown、删除笔记。主题笔记不会自动变成普通采集卡片或上传到 Obsidian。

## 隐私与一致性

- 只发送选定卡片的 ID、内容版本、正文；不发送标签、来源应用、来源 URL 或未选卡片。单卡最多 6000 字、合计最多 16000 字，超限拒绝而不是静默截断。
- 服务端模式使用固定配置的模型；BYOK 直接请求 Ark/OpenRouter，密钥不进入后端。界面展示发送路径，确认后若模型配置或来源版本已变化则要求重新选择。
- 客户端发送前与服务端接收后做敏感过滤。过滤只是纵深防护，不能代替用户对授权范围和第三方数据处理策略的确认。
- 模型输入在 user JSON 中，任务约束放在 system 消息中。引用 ID 必须来自选定集合、quote 必须逐字匹配对应原文；共同观点和分歧至少引用两张不同卡片，且全部已选卡片必须被覆盖。
- 引用匹配不等于推论正确。所有关系默认候选，必须人工确认；界面保留“模型推论需核对”的说明。
- 主题笔记、选定来源的历史快照和关系证据均由 Keystore 加密后落盘。普通正文修改会使关联失效；生成过程中来源修改/删除则丢弃结果。已保存笔记在来源变化后显示历史快照，不伪装成当前结论。
- 删除原卡片不会级联删除已保存主题笔记中的历史引用与快照。彻底移除这份归纳副本需单独删除笔记。删除笔记不删除已确认关系。
- 模型请求不自动重试，客户端禁止隐式连接重试及重定向。取消等待不保证服务商停止已接收的请求，也不保证免除已发生费用。

## 实现边界

- 本地召回用英文单词和中文双字片段的归一化重合分数；目前没有 Embedding、向量库或全库语义搜索。关键词检索只用于提供小规模候选，具体支持/反驳/补充/例证关系由用户选定后的 LLM 给出。
- 服务端 `POST /v1/knowledge:synthesize` 是有鉴权的无状态接口，不按客户端 ID 查询数据库、不持久化请求/结果、不触发发布。最多 2 个并发，20 秒超时，失败返回固定安全错误。
- 本地 `KnowledgeController` 管理确认、取消和反馈；`KnowledgeRepository` 在事务中校验内容版本，保存笔记和关系候选。拒绝过的卡片对不会因不同关系类型或重新归纳而重复出现。
- Room 5 -> 6 为关系表增加加密证据、来源版本和生成方式，新增仅含加密 payload 的主题笔记表。已有确认关系及正文保留。

## 验证与渐进上线

本地测试覆盖引用伪造、遗漏来源、单来源比较、输入边界、敏感过滤、提示词隔离、取消、内容变更后的晚到结果、本地关联排序与忽略、关系版本校验和迁移。使用 deterministic/模拟服务，不访问真实模型。

上线流程：本地测试通过 -> 人工批准 BOE 的模型/数据使用范围 -> 使用脱敏样本验证真实 provider 的格式兼容性、引用准确性、关联采纳率和延迟 -> 先上线兼容后端，再通过内部渠道小范围分发 Android -> 人工确认后逐步扩大范围。不得自动部署、绕过审批或使用真实用户知识库做隐式评估。

旧后端不支持新接口时显示失败，不自动更换 provider 或扩大上传范围。异常时人工关闭 AI，保留本地采集和关键词关联。Room v6 不能直接降级清库；优先前向修复。正式扩大范围前仍需真机 Room 迁移、Keystore、UI 可用性与实际模型效果评估。
